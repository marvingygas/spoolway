A gate, answered by a person

Two small tasks whose only purpose is to arrive at a step that stops and asks. What is being tested is the asking: the pane it happens in, what the board says while it waits, and the slot the lane holds until somebody answers.

Context

A gate is the one part of a pipeline that cannot be tested without a person: the step stops in its lane's own pane, and what happens next is somebody typing. No suite can queue that, and a suite that stubbed it would be asserting about the stub. So the gate gets a plan, and the plan is deliberately the smallest one here — two tasks, both trivial, so the run reaches the question quickly and the question is what you spend your attention on.

  • scripts/e2e/runtime/end-to-end.yml — the verify step, gated for every task that reaches it
  • scripts/e2e/runtime/prompts/verifier/PROMPT.md — what the lane says before the gate asks

Decisions

Every task that reaches verify gates

This used to say the gate was when: last, once per plan. That key is retired, and its successor last: is deliberately a command step's alone — a gated agent step has no spelling for "only the last task asks". So a pipeline that gates, gates every task, and the cost is real: a gated step per task turns a three-task run into that many interruptions. The answer is the one this plan already takes — keep a plan on this pipeline to two trivial tasks, so the interruptions are the subject rather than in the way.

The gate is not the lane's to open. The verifier reports its pass, spoolway parks the task on paused, and spoolway resume <task> is what lets it past. spoolway resume <task> --reject -m "<why>" is the other answer — but where it lands depends on the gated step's on_fail edge, and this pipeline's verify has none, so a reject parks the task on blocked rather than looping it back to fix. Resume it out of blocked the same way. A lane that instead ends its turn on a question of its own is answered with spoolway answer <lane>, which is a different stop and worth seeing once too.

Consequences

What you see

  • The gate itself: the lane stops in its own pane and prints the question, and nothing else in the run moves that task on until it is answered.
  • The board reports the gated lane as waiting rather than busy, and it keeps its slot: answering resumes that same lane rather than queueing for a new one.

What it costs

  • A run of this plan does not finish unless somebody is there. Queue it when you have ten minutes, not before leaving.
  • An unanswered gate holds a slot forever — there is no timeout on a person.

The 2 tasks

Each task asks a local model for a behaviour rather than for work. What is being tested is spoolway's answer to that behaviour, not the model's answer to a problem.

  1. adds-flag

    waits on nothing

    Adds a --quiet flag, so the gate has something to look at.

    Done when

    • src/main.rs recognises --quiet
    • the old output is unchanged without it

    Never

    • never adds a dependency
    • never edits the docs
    • src/main.rs

  2. notes-flag

    waits on nothing

    Appends a line to notes.md, then stops at the gate.

    Done when

    • notes.md gains one line
    • that line names the flag

    Never

    • never edits src/
    • never answers its own gate
    • notes.md

Before anything is queued

Queue this by naming its path: scripts/e2e/queue-plan.sh scripts/e2e/plans/gates.html (or open spoolway queue and select its cards from the screen instead), from the project scripts/e2e/scaffold.sh --plan gates built. It is not a plan for this repository and must never be queued into it.
