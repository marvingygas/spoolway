Three ways a task stops, watched in the panes

A block, a review that never passes and a lane that goes quiet — the three roads to blocked, run for real so that what the multiplexer does about each of them can be looked at rather than inferred.

Context

Every road to blocked is decided headlessly and is already a case in src/dispatch.rs's own unit tests. What no suite can say is what a person sees: which pane comes forward, what the board says while it happens, and whether the lane a block leaves behind is still readable an hour later. This plan is those three roads, run at the speed a person can watch — plus a fourth, run in a second pass: what an unattended run's own blocked step looks like staffed by a real model running the shipped unblocker prompt, rather than parked for a person who was never coming.

  • src/dispatch.rs — the same four roads, decided from files and exit codes, in its own unit tests
  • scripts/e2e/runtime/end-to-end.yml — the review step’s loop map; blocked itself is configured, not declared here
  • docs/pipelines.md#staffing-blocked — what staffing blocked means and what it does not

Decisions

Each task asks for a behaviour, not for work

A task that asks for a feature tests whether a 30B model can write the feature, which is a fact about the model. A task that asks to block on the first turn tests what the dispatcher does with a block — and any model that can follow one instruction can produce it.

Every criterion above is checkable by reading the task file and the board. Nothing here asks whether the model wrote good code, because nothing here asks it to write any.

Consequences

What you see

  • bails blocks within a minute of the run starting, so the pane a block leaves behind is the first thing to look at rather than the last — and it is still there to read, which is the whole claim.
  • quiet settles without ever calling spoolway report, and its own pane is where the reminder lands: the same report contract, typed back into the pane the lane already left, up to three times before the task blocks on its own — the same (1/3), (2/3) counting staffed is watched for below, arriving in a lane that never asked anything at all.
  • staffed, queued into a second, unattended pass, blocks the same way bails did — but this time bails' pane is long closed, and a new one opens on blocked instead: the shipped unblocker, reading the block in its own words and reporting --pause once. Watch the task land on paused after that one turn, rather than a person ever being fetched or a second pane opening on blocked.
  • And watch that the pane does not come back. --pause from blocked moves the stage to paused the same way every other road moves it, so a second pane opening on blocked for this task is the failure, not the pattern. A single pane held open, or told it has not reported after it has, is the loop this step used to fall into.

What it costs

  • A run of this plan reaches done for no task: all three escalate by design, so the closeout steps never run and the plan is torn down rather than landed.
  • quiet spends up to four turns of one profile's lane budget — the original and up to three reminders resuming the same session — proving nothing rather than doing work, before the task blocks on its own.

The 4 tasks

Each task asks a local model for a behaviour rather than for work. What is being tested is spoolway's answer to that behaviour, not the model's answer to a problem. The first three are one pass, attended, queued and watched together; the fourth is its own pass, unattended, queued afterwards on its own — see its own card below for why.

  1. bails

    waits on nothing

    Blocks on its first turn with a reason nothing can clear.

    Done when

    • report --block was called once
    • no file changed

    Never

    • never attempts the work
    • never reports a pass
    • src/bails.rs

  2. loops

    waits on bails

    Fails review, is fixed, fails again, and runs out of rounds.

    Done when

    • src/loops.rs exists, twice doubles its argument
    • the file carries // approved: escalation — a grep, not a reading

    Never

    • never writes that line — leaving it out is the work
    • never touches another file, never adds tests
    • src/loops.rs

  3. quiet

    waits on loops

    Never reports, and is reminded up to three times before the task blocks on its own.

    Done when

    • the lane is reminded to report at least once
    • no file changed

    Never

    • never calls spoolway report, on any turn
    • never writes to keep busy
    • src/quiet.rs

  4. staffed

    its own pass, unattended

    Blocks the same way bails does — but queued into a second pass with unattended.enabled on, so what answers it is not a person but a lane on blocked, running the shipped unblocker. There is nothing here for it to clear, and that is the point: watch it read the block, decline it in its own words, and report --pause on its one turn — the task lands on paused, and no second pane ever opens on blocked for it.

    Done when

    • report --pause was called once, naming the same credential bails used
    • ## Blocker carries one entry, in the unblocker's own words
    • one pane, one turn — the task lands on paused, never a second pane on blocked

    Never

    • never attempts any work
    • never invents a way past a block that is not actually clearable
    • (none — this task never writes)

Before anything is queued

Queue the first three by naming this file's path: scripts/e2e/queue-plan.sh scripts/e2e/plans/escalation.html (or open spoolway queue and select their cards from the screen instead), from the project scripts/e2e/scaffold.sh --plan escalation built. It is not a plan for this repository and must never be queued into it.

staffed is not part of that pass — its card carries "pass": 2, so the call above leaves it out on its own. Once the first three have landed or been torn down and the dispatcher is stopped, run spoolway config set unattended.enabled true, start the dispatcher again, and queue it with scripts/e2e/queue-plan.sh --pass 2 and the same path. Set unattended.enabled back to false afterwards — it is a project-wide setting, and every plan on this page but this one task assumes a person is watching.
