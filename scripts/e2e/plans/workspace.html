Two lanes, two worktrees, one file between them

Two chained tasks that both edit src/main.rs: enough to put two panes side by side in one shared workspace, and make the second task's worktree — cut from the first task's branch — start from an edit it must not clobber rather than from a clean file.

Context

Everything about a worktree, a workspace and a pane is decided by code with unit tests behind it and asserted headlessly with a fake multiplexer. None of that says whether the real one ends up with two readable panes, whether the tab is named something a person can find, or whether stopping the run leaves the screen tidy. This plan is two tasks big because two is the smallest number that produces a second of anything.

  • scripts/e2e/suites/stacking.sh — the same two tasks, decided from the forge rather than the screen
  • src/mux.rs — what a workspace, a tab and a pane are to spoolway

Decisions

The run is interrupted on purpose, once

tear_lanes_on_stop is the only setting whose observable is what disappears from a screen, and the only way to see it is to stop a dispatcher that has work in flight. Doing that costs the run: the second task restarts from whatever its branch holds.

Start the dispatcher again afterwards. The point of the setting is that the next run cuts a fresh worktree on the branch it finds and carries on, and a plan that stopped there would have watched only half of it.

Consequences

What you see

  • Two panes with two local models working in them at once, which is also the cheapest way to find out whether agents.pi.concurrency matches what the model server was actually started with.
  • The second task's worktree is cut from the first task's branch, so its copy of src/main.rs already declares the first module — because both tasks edit that file, that is the whole reason they both touch it.

What it costs

  • Interrupting the run mid-flight throws away whatever the running lane had not committed. That is the setting working, but it is still a lost turn.
  • Two tasks on one file is a conflict on purpose, so a run of this plan is slower than its size suggests — the second lane spends its time not clobbering the first's edit.

The 2 tasks

Each task asks a local model for a behaviour rather than for work. What is being tested is spoolway's answer to that behaviour, not the model's answer to a problem.

  1. one-pane

    waits on nothing

    Adds src/one.rs and declares it.

    Done when

    • one() returns 1
    • main.rs declares the module

    Never

    • never touches src/two.rs
    • never adds tests
    • src/one.rs
    • src/main.rs

  2. two-panes

    waits on one-pane

    Adds src/two.rs, and edits the same file the task below it did.

    Done when

    • two() returns 2
    • both modules are declared

    Never

    • never removes the other module
    • never renames anything
    • src/two.rs
    • src/main.rs

Before anything is queued
